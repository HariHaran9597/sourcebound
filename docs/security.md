# Security posture

## Current deployment boundary

The default mode is for local development on a trusted machine. It binds Compose service ports to loopback, disables authentication, and uses a fixed local organization. Do not expose that mode to a network or use sensitive documents.

Self-hosted deployments can enable OIDC. The browser uses the authorization-code flow with PKCE, keeps OIDC client state in session storage, and sends the access token as a bearer token. The API verifies issuer, audience, expiry, signing key, and the configured organization claim using OIDC discovery and JWKS. Each document operation and retrieval is scoped to that organization. The identity provider must put `organization_id` in the access token and `sourcebound_admin` in the top-level roles claim for administrators.

## Current controls

- PDF extension and file-signature checks; streaming upload limit defaults to 50 MiB.
- Shared fixed-window request limits for expensive Ask (20/min per user), PDF ingestion (6/min per user across new documents and versions), and failed-version reprocessing (10/min per user). Cross-user organization ceilings default to 500 Ask requests, 60 ingestion requests, and 100 reprocess requests per minute. PostgreSQL atomically coordinates both scopes across API processes. User buckets are keyed by organization and authenticated subject, or source IP in local authentication-disabled mode; organization buckets share one identity per organization. Keys are HMACed with `SOURCEBOUND_RATE_LIMIT_HMAC_KEY`, limited buckets are pruned by the retention worker, and over-limit responses include `429`, `Retry-After`, and `RateLimit-Scope`; successful responses describe the most restrictive active bucket. Tune the corresponding `SOURCEBOUND_*_RATE_LIMIT_PER_MINUTE` settings for the deployment. The sample key is development-only; generate a strong value and share it across API replicas through a secret manager.
- Organization quotas default to 1,000 logical documents and 10 GiB of uploaded PDF source bytes. Every retained immutable PDF version counts toward storage; deleting a document releases its document slot and all version bytes. Limits are configurable with `SOURCEBOUND_ORGANIZATION_MAX_DOCUMENTS` and `SOURCEBOUND_ORGANIZATION_MAX_STORAGE_BYTES`. `organization_usage` is backfilled by migration 0011 and upload/delete accounting is transactionally serialized per organization in PostgreSQL. This quota does not include parsed text, vector index size, backups, or answer history; it is not billing metering. The admin Knowledge view shows current source usage.
- Per-process request concurrency ceilings cap all API requests (default 200), Ask requests (8), and ingestion/reprocessing requests (2). Saturated work returns `503` with `Retry-After` after a bounded wait. These ceilings multiply across replicas; use ingress limits for a deployment-wide concurrency cap.
- Local SQLite rate limiting uses `INSERT .. ON CONFLICT .. RETURNING`; use SQLite 3.35 or newer. PostgreSQL is the recommended self-hosted deployment database.
- Original files and parsed artifacts stay in local/self-hosted storage.
- Organization-scoped metadata queries and vector filters.
- Optional per-document group allow-lists, checked against OIDC group claims in the API and vector retrieval; workspace admins retain access.
- Reusable organization group names are managed by workspace admins, backfilled from existing ACL values, and synchronized from verified uploader claims on document upload. Document policies select exact claim values. A group cannot be deleted while any document policy references it; admin group create/delete events are audited. Verified OIDC group claims are bounded to 100 values of at most 255 characters each.
- Curated document relationships are same-organization, workspace-admin-managed, audited metadata. Relationship listing hides inaccessible endpoints, and Ask only expands through linked documents already in the caller's authorized-document set. Relationship labels guide retrieval; cited source passages remain the evidence returned to the model and user.
- OIDC access-token verification fails closed when enabled.
- Retrieved evidence is presented as untrusted reference material; emitted citation numbers must map to the retrieved passage list. Unknown or missing citations cause a safe abstention, and the API returns only passages cited by the answer or its potential-conflict findings. Citation presence does not prove entailment.
- Potential conflict summaries are model-generated and must reference at least two retrieved passages. The API validates every passage reference, but it cannot prove the sources truly conflict; treat these as review prompts, not policy decisions.
- Conflict dispositions are user-scoped to the answer owner, require current access to all cited sources, and are recorded in the organization audit stream without the summary, review rationale, or source text. Optional review rationale is stored with sensitive answer history and follows its retention/deletion behavior.
- Answer history is enabled by default for self-hosted instances. It stores each user's question, generated answer, exact cited text, and model/retrieval version metadata in PostgreSQL for 30 days by default. Users can delete one entry or clear their own history; the retention worker removes expired entries. Set `SOURCEBOUND_STORE_ANSWER_TRACES=false` to disable it or change `SOURCEBOUND_ANSWER_TRACE_RETENTION_DAYS`. Treat this data with the same sensitivity as the source documents.
- Security-relevant document creation, version uploads, access-policy changes, and source deletion are recorded in an organization-scoped audit table; only workspace admins can read the latest events through `/api/v1/audit-events`. Source deletion removes stored versions and indexed points and deletes saved answer traces that cite the source. Deletion is blocked while any version is being processed. Deletion event metadata contains only version and affected-history counts, not document contents or answer text. Database administrators can still modify the underlying tables, so this is an application audit trail, not tamper-proof evidence storage.
- Compose data services bind to localhost; API and worker containers use a non-root account. The ingestion worker also has a read-only root filesystem, drops Linux capabilities, disables privilege escalation, and has configurable CPU/memory plus PID and temporary-storage limits. It still needs access to the source volume, database, broker, Qdrant, and model cache; this is a hardened container boundary, not a hostile-file sandbox.

## Known gaps before production use

- Document policies still store exact group-name strings on each document rather than normalized membership grants or reusable policy bundles. The organization group catalog is a reusable name directory, not a full policy engine.
- Stronger parser isolation (including restricted network access), malware scanning, encrypted object storage, key rotation, backup/restore drills, and a security review remain to be done. Request-rate ceilings and document/source-byte quotas are enforced organization-wide; source-byte quotas do not account for parsed pages or derived/vector storage. Worker CPU and memory ceilings are configurable with `WORKER_CPUS` and `WORKER_MEMORY_LIMIT` in the Compose environment; choose them for the host and expected PDF workload. Enforce ingress rate and body-size limits at the reverse proxy too, because multipart uploads reach the API before the endpoint handler applies its request counter.
- Prompt-injection resistance and answer accuracy have not been measured. The evaluation runner can now record forbidden-source citation and literal canary hit rates, but no red-team run is included and these checks cannot detect paraphrased disclosure. Citation-ID validation prevents invented source IDs, but does not prove that every claim is supported by cited text.
- Browser tokens are held in session storage. A stricter deployment can put the UI behind a backend-for-frontend session boundary.
- There is no external penetration test or compliance assessment. Do not describe the current build as certified, audited, or production-hardened.

## Deployment requirements

Before opening a deployment beyond localhost, enable OIDC, configure organization and role claims, terminate TLS at a maintained reverse proxy, replace example credentials, restrict database/vector/queue networks, configure secret management, and establish backups and retention policies.
